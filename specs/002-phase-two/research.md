## 1. Authentication Architecture

### Research Question
Better Auth integration pattern with FastAPI backend and Next.js frontend.

### Finding
**Better Auth is JavaScript/TypeScript only** - it is NOT a Python library. The constitution reference to "Better Auth (or equivalent Python auth library)" requires clarification.

### Decision
**Use JWT-based authentication with FastAPI's built-in security utilities**

**Backend Stack:**
- `python-jose[cryptography]` - JWT token creation and validation
- `passlib[bcrypt]` - Password hashing
- `python-multipart` - Form data handling
- FastAPI's `OAuth2PasswordBearer` and `OAuth2PasswordRequestForm`

**Frontend Stack:**
- Custom authentication utilities (no external auth library needed)
- HTTP-only cookies for token storage (preferred) or localStorage
- `credentials: 'include'` in fetch requests

**Token Flow:**
1. User submits credentials to `/auth/token` endpoint
2. FastAPI validates credentials, returns JWT access token
3. Next.js stores token in HTTP-only cookie (secure)
4. Next.js includes token in `Authorization: Bearer <token>` header
5. FastAPI validates JWT using dependency injection

**Security Practices:**
- Bcrypt password hashing (via passlib)
- Short-lived access tokens (15-30 minutes)
- HTTP-only cookies to prevent XSS attacks
- HTTPS only in production
- Rate limiting on auth endpoints

### Rationale
- Python-native solution (no JavaScript library confusion)
- Stateless and scalable
- Industry-standard OAuth2 pattern
- Well-supported by FastAPI
- Simple to implement and maintain

## 2. Database Migrations

### Research Question
SQLModel schema migration strategy for production database management.

### Finding
**SQLModel does NOT have built-in migration support.** The `SQLModel.metadata.create_all(engine)` method only creates tables that don't exist - it cannot handle schema changes.

### Decision
**Use Alembic for database migrations**

**Migration Tool:** Alembic (official SQLAlchemy migration tool)

**Why Alembic:**
- Industry standard for Python database migrations
- Full compatibility with SQLModel (built on SQLAlchemy)
- Autogenerate feature detects schema changes
- Version control for database schema
- Rollback capabilities

**Workflow:**

```bash
# Install
pip install alembic psycopg2-binary

# Initialize
alembic init alembic

# Create migration
alembic revision --autogenerate -m "description"

# Apply migration
alembic upgrade head

# Rollback
alembic downgrade -1
```

**Configuration:**
- Set `target_metadata = SQLModel.metadata` in `alembic/env.py`
- Configure Neon PostgreSQL connection string
- Use `NullPool` for migration operations (serverless-friendly)

**Best Practices:**
- One logical change per migration
- Always review autogenerated migrations
- Test both upgrade and downgrade paths
- Commit migration files to version control
- Backup database before production migrations

### Rationale
- No viable alternatives for SQLModel
- Production-grade schema management
- Autogenerate saves time and reduces errors
- Rollback capability for safety

## 3. Neon PostgreSQL Connection

### Research Question
Neon Serverless PostgreSQL connection configuration and best practices.

### Finding
Neon provides two connection types: **pooled** (recommended) and **direct**.

### Decision
**Use pooled connections with conservative pool settings**

**Connection String Format:**
```
postgresql://[user]:[password]@[endpoint]-pooler.neon.tech/[dbname]?sslmode=require
```

**SQLModel Engine Configuration:**

```python
from sqlmodel import create_engine

engine = create_engine(
    DATABASE_URL,
    echo=False,  # Set to True for debugging
    pool_pre_ping=True,  # Verify connections before use
    pool_size=5,  # Number of connections to maintain
    max_overflow=10,  # Additional connections when pool is full
    pool_recycle=3600,  # Recycle connections after 1 hour
    connect_args={
        "sslmode": "require",  # Enforce SSL (required by Neon)
        "connect_timeout": 10,  # Connection timeout in seconds
        "application_name": "fastapi-app",  # Helps with monitoring
    }
)
```

**Environment Variables:**
```env
DATABASE_URL=postgresql://user:pass@ep-xxx-pooler.us-east-2.aws.neon.tech/neondb?sslmode=require
DB_POOL_SIZE=5
DB_MAX_OVERFLOW=10
DB_POOL_RECYCLE=3600
```

**Key Considerations:**
- Always use `-pooler` endpoint for serverless applications
- Conservative pool sizes (5-10 connections) for Neon serverless
- Enable `pool_pre_ping=True` for reliability
- Set `pool_recycle=3600` to prevent stale connections
- SSL is required (`sslmode=require`)

### Rationale
- Optimized for serverless PostgreSQL
- Prevents connection exhaustion
- Handles connection failures gracefully
- Production-ready configuration

## 4. Frontend-Backend API Communication

### Research Question
FastAPI-Next.js API communication patterns (CORS, API client, authentication headers).

### Finding
Next.js App Router works best with native `fetch` due to built-in caching, revalidation, and Server Component support.

### Decision
**Custom API client based on native fetch**

**CORS Configuration (FastAPI):**

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],  # Specific origins
    allow_credentials=True,  # Required for cookies/auth
    allow_methods=["GET", "POST", "PUT", "DELETE", "PATCH"],
    allow_headers=["Content-Type", "Authorization"],
    max_age=3600,  # Cache preflight requests
)
```

**API Client Pattern (Next.js):**

```typescript
class ApiClient {
  private baseURL: string;

  async request<T>(endpoint: string, config: RequestInit = {}): Promise<T> {
    const url = `${this.baseURL}${endpoint}`;
    const token = this.getAuthToken();

    const response = await fetch(url, {
      ...config,
      credentials: 'include',  // Send cookies
      headers: {
        'Content-Type': 'application/json',
        ...(token && { Authorization: `Bearer ${token}` }),
        ...config.headers,
      },
    });

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    return response.json();
  }

  async get<T>(endpoint: string): Promise<T> {
    return this.request<T>(endpoint, { method: 'GET' });
  }

  async post<T>(endpoint: string, data: unknown): Promise<T> {
    return this.request<T>(endpoint, {
      method: 'POST',
      body: JSON.stringify(data),
    });
  }
}

export const apiClient = new ApiClient(
  process.env.NEXT_PUBLIC_API_URL || 'http://localhost:8000'
);
```

**Authentication Header Management:**
- HTTP-only cookies (preferred): Automatic with `credentials: 'include'`
- localStorage: Manual token retrieval and Authorization header

**Error Handling:**
- Custom `ApiError` class with status codes
- React hooks for loading/error states
- Error boundaries for Server Components

**Environment Variables:**
```env
# Next.js (.env.local)
NEXT_PUBLIC_API_URL=http://localhost:8000

# FastAPI (.env)
CORS_ORIGINS=["http://localhost:3000"]
```

### Rationale
- Zero additional bundle size (native fetch)
- Full Next.js caching and revalidation support
- Works in both Server and Client Components
- Request deduplication out of the box
- Better performance than Axios for Next.js

## 5. Session/Token Management

### Research Question
Session/token management strategy between frontend and backend.

### Decision
**JWT tokens with HTTP-only cookies**

**Token Strategy:**
- **Access Token**: Short-lived (15-30 minutes), stored in HTTP-only cookie
- **Token Type**: JWT (JSON Web Token)
- **Storage**: HTTP-only cookie (prevents XSS attacks)
- **Transmission**: Automatic via `credentials: 'include'`

**Backend Implementation:**
```python
from datetime import datetime, timedelta
from jose import jwt

def create_access_token(data: dict, expires_delta: timedelta = None):
    to_encode = data.copy()
    expire = datetime.utcnow() + (expires_delta or timedelta(minutes=30))
    to_encode.update({"exp": expire})
    return jwt.encode(to_encode, SECRET_KEY, algorithm="HS256")

@app.post("/auth/login")
async def login(response: Response):
    token = create_access_token({"sub": user.id})
    response.set_cookie(
        key="auth_token",
        value=token,
        httponly=True,  # Prevents JavaScript access
        secure=True,    # HTTPS only (production)
        samesite="lax", # CSRF protection
        max_age=1800,   # 30 minutes
    )
    return {"message": "Login successful"}
```

**Frontend Implementation:**
```typescript
// Login
await fetch('/auth/login', {
  method: 'POST',
  credentials: 'include',  // Send/receive cookies
  body: JSON.stringify({ username, password }),
});

// Authenticated requests
await fetch('/api/todos', {
  credentials: 'include',  // Automatically sends auth cookie
});
```

**Alternative (localStorage):**
- Store token in localStorage
- Manually add `Authorization: Bearer <token>` header
- Less secure (vulnerable to XSS)
- Simpler implementation

### Rationale
- HTTP-only cookies prevent XSS attacks
- Automatic cookie handling by browser
- No manual token management needed
- Industry best practice for web applications
